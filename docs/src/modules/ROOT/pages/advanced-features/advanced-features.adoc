GreyCOS Solver includes advanced features for scaling out to large and complex planning problems.
These features are particularly useful when solving problems with huge datasets or when you need to maximize performance on multi-core hardware.

The following sections describe these advanced features in detail.

[#advancedFeaturesList]
== Advanced Features

The following advanced features are available in GreyCOS Solver:

* <<nearbySelection,Nearby selection>>
* <<multithreadedIncrementalSolving,Multi-threaded incremental solving>>
* <<partitionedSearch,Partitioned search>>
* <<islandModel,Island model>>
* <<automaticNodeSharing,Automatic node sharing>>
* <<throttlingBestSolutionEvents,Throttling best solution events>>


[#nearbySelection]
=== Nearby selection

Nearby selection gives closer entities or values a higher probability of selection.
For problems such as TSP and VRP, this can improve solution quality within the available solving time.

image::advanced-features/nearbySelectionMotivation.png[align="center"]

The benefit depends on the distance meter, neighborhood, and dataset; measure it on representative problems:

image::advanced-features/nearbySelectionValueProposition.png[align="center"]

Nearby selection increases the probability of selecting an entity or value which is nearby to the first entity being moved in that move.

image::advanced-features/nearbySelectionRandomDistribution.png[align="center"]

The distance between two entities or values is domain specific.
Therefore, implement the `NearbyDistanceMeter` interface:

[tabs]
====
Java::
+
[source,java,options="nowrap"]
----
public interface NearbyDistanceMeter<Origin_, Destination_> {

    double getNearbyDistance(Origin_ origin, Destination_ destination);

}
----
====

The `Origin_` and `Destination_` types are determined by the selectors carrying `nearbySelection`.
For a basic variable, `Origin_` is the planning entity and `Destination_` may be a planning value or entity.
For a list variable, `Origin_` is a planning value, while `Destination_` may be a planning value or entity.
A sublist origin is represented by its first planning value at the time the sublist is selected.
The meter receives that value, not a `SubList` object.
For example, in vehicle routing the distance meter must accept both `Customer` and `Vehicle` destinations:

[tabs]
====
Java::
+
[source,java,options="nowrap"]
----
public class CustomerNearbyDistanceMeter implements NearbyDistanceMeter<Customer, LocationAware> {

    public double getNearbyDistance(Customer origin, LocationAware destination) {
        return origin.getDistanceTo(destination);
    }

}
----
====

[NOTE]
====
`NearbyDistanceMeter` implementations must be stateless and thread-safe.
Distances are cached during a solver phase, so calculate them from facts that remain constant during that phase,
such as customer coordinates, rather than from changing route positions or planning variables.
The solver may reuse the meter in different contexts.

The Nearby configuration is not enabled for the Construction Heuristics
because the method will analyze all possible moves.
Adding Nearby in this situation would only result in unnecessary costs
involving the generation of the distance matrix and sorting operations without taking advantage of the feature.
====

[#basicVariableNearbySelection]
==== Nearby selection with a basic variable

To configure nearby selection for a solution that only uses basic variables,
set `nearbyDistanceMeterClass` at solver level:

[source,xml,options="nowrap"]
----
<solver xmlns="https://greycos.ai/xsd/solver">
  ...
  <nearbyDistanceMeterClass>org.acme.schooltimetabling.cotwin.solver.nearby.LectureNearbyDistanceMeter</nearbyDistanceMeterClass>
  ...
</solver>
----

The default Local Search neighborhood then includes Change, Swap, Change with Nearby and Swap with Nearby.
Solver-level automatic nearby configuration also supports mixed basic/list models.
Its distance meter must accept the origin and destination types used by both kinds of variable.
Use explicit move-selector configuration when different variables require different distance meters.

For advanced configuration, add `nearbySelection` to a change move's `valueSelector`
or a swap move's `secondaryEntitySelector` and use mimic selection to identify the origin:

[source,xml,options="nowrap"]
----
<unionMoveSelector>
  <changeMoveSelector>
    <entitySelector id="entitySelector1"/>
    <valueSelector variableName="room">
      <nearbySelection>
        <originEntitySelector mimicSelectorRef="entitySelector1"/>
        <nearbyDistanceMeterClass>org.acme.schooltimetabling.cotwin.solver.nearby.LectureNearbyDistanceMeter</nearbyDistanceMeterClass>
      </nearbySelection>
    </valueSelector>
  </changeMoveSelector>
  <swapMoveSelector>
    <entitySelector id="entitySelector2"/>
    <secondaryEntitySelector>
      <nearbySelection>
        <originEntitySelector mimicSelectorRef="entitySelector2"/>
        <nearbyDistanceMeterClass>org.acme.schooltimetabling.cotwin.solver.nearby.LectureNearbyDistanceMeter</nearbyDistanceMeterClass>
      </nearbySelection>
    </secondaryEntitySelector>
  </swapMoveSelector>
</unionMoveSelector>
----

For Change, the origin is the selected entity and the destination is the selected planning value.
For Swap, both are planning entities.

==== Nearby selection with a chained variable

The current planning-variable API supports basic and list variables.
Represent routes as planning list variables and configure nearby selection as described in
<<listVariableNearbySelection,Nearby selection with a list variable>>.
Legacy chained-variable and `tailChainSwapMoveSelector` configurations are not supported.

==== Power-tweaking distribution type

The solver allows you to tweak the distribution type of the nearby selection,
or how likely are the nearest elements to be selected based on their distance from the current.

[NOTE]
====
Only tweak the default settings if you are prepared
to back your choices by extensive xref:using-greycos-solver/benchmarking-and-tweaking.adoc#benchmarker[benchmarking].
====

The following ``NearbySelectionDistributionType``s are supported:

* `PARABOLIC_DISTRIBUTION`: Nearest elements are selected with a higher probability.
+
[source,xml,options="nowrap"]
----
  <nearbySelection>
    <parabolicDistributionSizeMaximum>80</parabolicDistributionSizeMaximum>
  </nearbySelection>
----
+
A `distributionSizeMaximum` parameter should not be 1 because if the nearest is already the planning value of the current entity,
then the only move that is selectable is not doable.
To allow every element to be selected regardless of the number of entities,
only set the distribution type (so without a `distributionSizeMaximum` parameter):
+
[source,xml,options="nowrap"]
----
  <nearbySelection>
    <nearbySelectionDistributionType>PARABOLIC_DISTRIBUTION</nearbySelectionDistributionType>
  </nearbySelection>
----
* ``BLOCK_DISTRIBUTION``: Only the n nearest are selected, with an equal probability. For example, select the 20 nearest:
+
[source,xml,options="nowrap"]
----
  <nearbySelection>
    <blockDistributionSizeMaximum>20</blockDistributionSizeMaximum>
  </nearbySelection>
----
* ``LINEAR_DISTRIBUTION`` (default): Nearest elements are selected with a higher probability. The probability decreases linearly.
+
[source,xml,options="nowrap"]
----
  <nearbySelection>
    <linearDistributionSizeMaximum>40</linearDistributionSizeMaximum>
  </nearbySelection>
----
* ``BETA_DISTRIBUTION``: Selection according to a beta distribution. Slows down the solver significantly.
+
[source,xml,options="nowrap"]
----
  <nearbySelection>
    <betaDistributionAlpha>1</betaDistributionAlpha>
    <betaDistributionBeta>5</betaDistributionBeta>
  </nearbySelection>
----


The distribution type may be omitted when its parameters identify it unambiguously.
For example, `parabolicDistributionSizeMaximum` selects the parabolic distribution.
Supplying parameters from more than one distribution is invalid.
Beta parameters must be finite and positive.
The block size ratio and uniform distribution probability must be finite and between 0 and 1, inclusive.
Invalid parameters are rejected when the solver is built.

For block selection, `blockDistributionSizeRatio` applies to the full eligible population before
`blockDistributionSizeMinimum` and `blockDistributionSizeMaximum` are applied.
With 1,000 eligible destinations, a ratio of 0.5 and a maximum of 100 select the nearest 100.
`blockDistributionUniformDistributionProbability` allows a uniform sample from the eligible population,
including destinations outside that block.

===== Distance caching and explicit truncation

Distance rows are initialized lazily and reused during a phase.
A bounded distribution can retain only the nearest candidates, but constructing a row still evaluates
the distance to every candidate. This is not a spatial index.
Setting `eagerInitialization` to `true` initializes enumerable origins at phase start;
it does not change the distribution or repeat rows already initialized by a shared selector.
For a sublist origin, eager initialization enumerates the planning values that can represent its first element.

`maxNearbySortSize` is an optional explicit cap on the retained neighborhood for random selection.
Leaving it unset preserves the distribution's full support; there is no automatic 1,000-destination cutoff.
Setting it limits which destinations can be selected, including uniform exploration, so it can change solution quality.
When eligibility can change during a phase, the solver retains a full distance row and applies the cap
after checking the current custom filters, assignments, and entity-specific ranges.
Changes in eligibility reuse the cached distances; they do not permanently remove candidates from the row.
Pinned, filtered-out, or unreachable destinations do not consume the eligible neighborhood.
For nearby sublists, a configured value filter applies to the first value of the candidate sublist;
the selected length must also satisfy the sublist bounds and both entity ranges.
The unassignment option, when supported by the planning variable, remains available separately from distance ranks.
Original-order nearby selection visits destinations in distance order without random truncation.

Bounded linear, parabolic, and beta sampling can stop checking candidates once the eligible neighborhood is full.
Block sampling and the unassignment probability still require the complete eligible population count.
Full distance rows may therefore remain necessary even when a small sampling cap is configured.


[#multithreadedSolving]
=== Multi-threaded solving

Multi-threaded solving is a term
which encapsulates several features that allow GreyCOS Solver to run on multi-core machines.
GreyCOS Solver supports powerful multi-threaded solving features including
<<multithreadedIncrementalSolving,multi-threaded incremental solving>> and
<<partitionedSearch,partitioned search>>.

For a primer on multi-threaded solving in general, see xref:using-greycos-solver/running-the-solver.adoc#multithreadedSolving[Multi-threaded solving].

[#multithreadedIncrementalSolving]
==== Multi-threaded incremental solving

With this feature, the solver can run significantly faster,
getting you the right solution earlier.
It has been designed to speed up the solver in cases where move evaluation is the bottleneck.
This typically happens when the constraints are computationally expensive,
or when the dataset is large.

- The sweet spot for this feature is when the move evaluation speed is up to 10 thousand per second.
In this case, we have observed the algorithm to scale linearly with the number of move threads.
Every additional move thread will bring a speedup,
albeit with diminishing returns.
- For move evaluation speeds on the order of 100 thousand per second,
the algorithm no longer scales linearly,
but using 4 to 8 move threads may still be beneficial.
- For even higher move evaluation speeds,
the feature does not bring any benefit.
At these speeds, move evaluation is no longer the bottleneck.
If the solver continues to underperform,
perhaps you're suffering from xref:constraints-and-score/performance.adoc#scoreTrap[score traps]
or you may benefit from xref:optimization-algorithms/overview.adoc#customMoves[custom moves]
to help the solver escape local optima.

[NOTE]
====
These guidelines are strongly dependent on move selector configuration,
size of the dataset and performance of individual constraints.
We recommend you benchmark your use case
to determine the optimal number of move threads for your problem.
====

===== Enabling multi-threaded incremental solving

Enable multi-threaded incremental solving
by xref:using-greycos-solver/modeling-planning-problems.adoc#planningId[adding a `@PlanningId` annotation]
on every planning entity class and planning value class.
Then configure a `moveThreadCount`:

[tabs]
====
Quarkus::
+
--
Add the following to your `application.properties`:

[source,properties]
----
quarkus.greycos.solver.move-thread-count=AUTO
----
--
Spring::
+
--
Add the following to your `application.properties`:

[source,properties]
----
greycos.solver.move-thread-count=AUTO
----
--
Java::
+
--
Use the `SolverConfig` class:

[source,java,options="nowrap"]
----
SolverConfig solverConfig = new SolverConfig()
    ...
    .withMoveThreadCount("AUTO");
----
--
XML::
+
--
Add the following to your `solverConfig.xml`:
[source,xml,options="nowrap"]
----
<solver xmlns="https://greycos.ai/xsd/solver" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
xsi:schemaLocation="https://greycos.ai/xsd/solver https://greycos.ai/xsd/solver/solver.xsd">

    ...
    <moveThreadCount>AUTO</moveThreadCount>
    ...

</solver>
----
--
====

Setting `moveThreadCount` to `AUTO` allows GreyCOS Solver to decide how many move threads to run in parallel.
This formula is based on experience and does not hog all CPU cores on a multi-core machine.

A `moveThreadCount` of `4` xref:integration/integration.adoc#sizingHardwareAndSoftware[saturates almost 5 CPU cores].
the 4 move threads fill up 4 CPU cores completely
and the solver thread uses most of another CPU core.

The following ``moveThreadCount``s are supported:

* `NONE` (default): Don't run any move threads. Use the single threaded code.
* ``AUTO``: Let GreyCOS Solver decide how many move threads to run in parallel.
On machines or containers with little or no CPUs, this falls back to the single threaded code.
* Static number: The number of move threads to run in parallel.

It is counter-effective to set a `moveThreadCount`
that is higher than the number of available CPU cores,
as that will slow down the move evaluation speed.

[IMPORTANT]
====
In cloud environments where resource use is billed by the hour,
consider the trade-off between cost of the extra CPU cores needed and the time saved.
Compute nodes with higher CPU core counts are typically more expensive to run
and therefore you may end up paying more for the same result,
even though the actual compute time needed will be less.
====

[NOTE]
====
Multi-threaded solving is _still reproducible_, as long as the resolved `moveThreadCount` is stable.
A run of the same solver configuration on 2 machines with a different number of CPUs,
is still reproducible, unless the `moveThreadCount` is set to `AUTO` or a function of `availableProcessorCount`.
====

===== Advanced configuration

Move workers retain separate incremental working solutions and evaluate candidates concurrently.
The solver thread consumes results in selection order and makes all acceptance decisions.
Workers apply each selected step exactly once before evaluating candidates for that step.
Two bounded generations of work allow ready workers to continue while others finish the preceding step;
the solver waits for acknowledgements before reusing the older generation.

The candidate window is `moveThreadCount * moveThreadBufferSize`, with a default buffer of ten per worker.
A larger window can keep workers busy when evaluation times vary, but also increases serial move generation
and candidates discarded when foraging stops early.
Compare useful move evaluations, completed steps and solution quality when tuning the worker count and buffer.
The score-calculation count also includes worker setup, speculative calculations and coordinator accounting,
and therefore is not a count of useful evaluated moves.

For separate diagnostic runs, `-Dgreycos.solver.moveThreadDiagnostics=true` enables sampled worker timings
and coordinator wait timings. The internal deciders expose final pipeline counters after the phase ends;
these counters distinguish generated, evaluated, scored, consumed and discarded candidates.
Discarded counts include completed evaluations that were not consumed, but exclude cancelled candidates
that were never evaluated. Result-retrieval timings include ready-result handling as well as waiting.
Leave diagnostic timing disabled for throughput comparisons.

There are additional parameters you can supply to your `solverConfig.xml`:

[source,xml,options="nowrap"]
----
<solver xmlns="https://greycos.ai/xsd/solver" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="https://greycos.ai/xsd/solver https://greycos.ai/xsd/solver/solver.xsd">
  <moveThreadCount>4</moveThreadCount>
  <threadFactoryClass>...MyAppServerThreadFactory</threadFactoryClass>
  ...
</solver>
----

To run in an environment that doesn't like arbitrary thread creation,
use `threadFactoryClass` to plug in a <<customThreadFactory,custom thread factory>>.


[#partitionedSearch]
==== Partitioned search

[#partitionedSearchAlgorithm]
===== Algorithm description

It is often more efficient to partition large data sets (usually above 5000 planning entities)
into smaller pieces and solve them separately.
Partition Search is <<multithreadedSolving,multi-threaded>>,
so it provides a performance boost on multi-core machines due to higher CPU utilization.
Additionally, even when only using one CPU, it finds an initial solution faster,
because the search space sum of a partitioned Construction Heuristic is far less than its non-partitioned variant.

However, **partitioning does lead to suboptimal results**, even if the pieces are solved optimally, as shown below:

image::advanced-features/mapReduceIsTerribleForTsp.png[align="center"]

It effectively trades a short term gain in solution quality for long term loss.
One way to compensate for this loss,
is to run a non-partitioned Local Search after the Partitioned Search phase.

[NOTE]
====
Not all use cases can be partitioned.
Partitioning only works for use cases where the planning entities and value ranges can be split into n partitions,
without any of the constraints crossing boundaries between partitions.
====

[WARNING]
====
Models with xref:using-greycos-solver/modeling-planning-problems.adoc#chainedPlanningVariable[chained variables] cannot apply the partitioned search method.
====

[#partitionedSearchConfiguration]
===== Configuration

Simplest configuration:

[source,xml,options="nowrap"]
----
  <partitionedSearch>
    <solutionPartitionerClass>...MyPartitioner</solutionPartitionerClass>
  </partitionedSearch>
----

Also xref:using-greycos-solver/modeling-planning-problems.adoc#planningId[add a `@PlanningId` annotation]
on every planning entity class and planning value class.
There are several ways to <<partitioningASolution,partition a solution>>.

Advanced configuration:

[source,xml,options="nowrap"]
----
  <partitionedSearch>
    ...
    <solutionPartitionerClass>...MyPartitioner</solutionPartitionerClass>
    <runnablePartThreadLimit>4</runnablePartThreadLimit>

    <constructionHeuristic>...</constructionHeuristic>
    <localSearch>...</localSearch>
  </partitionedSearch>
----

The `runnablePartThreadLimit` allows limiting CPU usage to avoid hanging your machine, see below.

To run in an environment that doesn't like arbitrary thread creation,
plug in a <<customThreadFactory,custom thread factory>>.

[IMPORTANT]
====
A xref:using-greycos-solver/running-the-solver.adoc#logging[logging level] of `debug` or `trace` causes congestion in multi-threaded Partitioned Search
and slows down the xref:constraints-and-score/performance.adoc#moveEvaluationSpeed[move evaluation speed].
====

Just like a `<solver>` element,
the `<partitionedSearch>` element can contain one or more xref:optimization-algorithms/overview.adoc#solverPhase[phases].
Each of those phases will be run on each partition.

A common configuration is to first run a Partitioned Search phase
(which includes a Construction Heuristic and a Local Search)
followed by a non-partitioned Local Search phase:

[source,xml,options="nowrap"]
----
  <partitionedSearch>
    <solutionPartitionerClass>...MyPartitioner</solutionPartitionerClass>

    <constructionHeuristic/>
    <localSearch>
      <termination>
        <diminishedReturns />
      </termination>
    </localSearch>
  </partitionedSearch>
  <localSearch/>
----

[#customSolutionPartitioner]
====== Custom `SolutionPartitioner`

To use a custom `SolutionPartitioner`, configure one on the Partitioned Search phase:

[source,xml,options="nowrap"]
----
  <partitionedSearch>
    <solutionPartitionerClass>...MyPartitioner</solutionPartitionerClass>
  </partitionedSearch>
----

Implement the `SolutionPartitioner` interface:

[source,java,options="nowrap"]
----
public interface SolutionPartitioner<Solution_> {

    List<Solution_> splitWorkingSolution(ScoreDirector<Solution_> scoreDirector, Integer runnablePartThreadLimit);

}
----

The `size()` of the returned `List` is the `partCount` (the number of partitions).
This can be decided dynamically, for example, based on the size of the non-partitioned solution.
The `partCount` is unrelated to the `runnablePartThreadLimit`.

To configure values of a `SolutionPartitioner` dynamically in the solver configuration
(so the xref:using-greycos-solver/benchmarking-and-tweaking.adoc#benchmarker[Benchmarker] can tweak those parameters),
add the `solutionPartitionerCustomProperties` element and use xref:using-greycos-solver/configuration.adoc#customPropertiesConfiguration[custom properties]:

[source,xml,options="nowrap"]
----
  <partitionedSearch>
    <solutionPartitionerClass>...MyPartitioner</solutionPartitionerClass>
    <solutionPartitionerCustomProperties>
      <property name="myPartCount" value="8"/>
      <property name="myMinimumProcessListSize" value="100"/>
    </solutionPartitionerCustomProperties>
  </partitionedSearch>
----

[#runnablePartThreadLimit]
===== Runnable part thread limit

When running a multi-threaded solver, such as Partitioned Search, CPU power can quickly become a scarce resource,
which can cause other processes or threads to hang or freeze.
However, GreyCOS Solver has a system to prevent CPU starving of
other processes (such as an SSH connection in production or your IDE in development)
or other threads (such as the servlet threads that handle REST requests).

As explained in xref:integration/integration.adoc#sizingHardwareAndSoftware[sizing hardware and software],
each solver (including each child solver) does no IO during `solve()` and therefore saturates one CPU core completely.
In Partitioned Search, every partition always has its own thread, called a part thread.
It is impossible for two partitions to share a thread,
because of xref:optimization-algorithms/overview.adoc#asynchronousTermination[asynchronous termination]:
the second thread would never run.
Every part thread will try to consume one CPU core entirely, so if there are more partitions than CPU cores,
this will probably hang the system.
`Thread.setPriority()` is often too weak to solve this hogging problem, so another approach is used.

The `runnablePartThreadLimit` parameter specifies how many part threads are runnable at the same time.
The other part threads will temporarily block and therefore will not consume any CPU power.
*This parameter basically specifies how many CPU cores are donated to GreyCOS Solver.*
All part threads share the CPU cores in a round-robin manner
to consume (more or less) the same number of CPU cycles:

image::advanced-features/partitionedSearchThreading.png[align="center"]

The following `runnablePartThreadLimit` options are supported:

* `UNLIMITED`: Allow GreyCOS Solver to occupy all CPU cores, do not avoid hogging.
Useful if a no hogging CPU policy is configured on the OS level.
* `AUTO` (default): Let GreyCOS Solver decide how many CPU cores to occupy. This formula is based on experience.
It does not hog all CPU cores on a multi-core machine.
* Static number: The number of CPU cores to consume. For example:
+
[source,xml,options="nowrap"]
----
<runnablePartThreadLimit>2</runnablePartThreadLimit>
----

[WARNING]
====
If the `runnablePartThreadLimit` is equal to or higher than the number of available processors,
the host is likely to hang or freeze,
unless there is an OS specific policy in place to avoid GreyCOS Solver from hogging all the CPU processors.
====

The `threadFactoryClass` allows to plug in a custom `ThreadFactory` for environments

  ...
</solver>
----

[#islandModel]
=== Island model

The island model is a parallel evolutionary computation paradigm that enhances solution quality by running multiple independent searches in parallel.

Islands operate as separate agents, each running the same phases with independent random seeds and solution states.
These islands periodically exchange their best solutions through migration in a ring topology,
allowing better solutions to propagate across the population.

This approach can significantly improve solution quality on complex optimization problems
by maintaining diversity in the search process and enabling parallel exploration of different areas of the solution space.

[IMPORTANT]
====
The island model requires xref:using-greycos-solver/modeling-planning-problems.adoc#planningId[`@PlanningId` annotations]
on all planning entity and planning value classes to enable solution cloning and migration.
====


[#automaticNodeSharing]
=== Automatic node sharing

When a `ConstraintProvider` repeats an operation in multiple constraints, such as finding all shifts for an employee,
node sharing can perform that work once.
Automatic node sharing identifies eligible equivalent lambdas and method references so more constraint stream nodes can be shared.
The effect on move evaluation speed and memory use depends on the constraints and problem; measure it with your own workload:

image::advanced-features/nodeSharingValueProposition.png[align="center"]

==== Configuration

Automatic node sharing is disabled by default.
It is available in plain Java, Spring Boot and Quarkus JVM applications.
It is unsupported in native images; enabling it there causes startup to fail.

[tabs]
====
Plain Java::

* Add `<constraintStreamAutomaticNodeSharing>true</constraintStreamAutomaticNodeSharing>` in your `solverConfig.xml`:
+
[source,xml,options="nowrap"]
----
<!-- ... -->
<scoreDirectorFactory>
  <constraintProviderClass>org.acme.MyConstraintProvider</constraintProviderClass>
  <constraintStreamAutomaticNodeSharing>true</constraintStreamAutomaticNodeSharing>
</scoreDirectorFactory>
<!-- ... -->
----

Spring Boot::

Set the property `greycos.solver.constraint-stream-automatic-node-sharing` to `true` in `application.properties`:
+
[source,properties,options="nowrap"]
----
greycos.solver.constraint-stream-automatic-node-sharing=true
----

Quarkus::

Set the property `quarkus.greycos.solver.constraint-stream-automatic-node-sharing` to `true` in `application.properties`:
+
[source,properties,options="nowrap"]
----
quarkus.greycos.solver.constraint-stream-automatic-node-sharing=true
----
====

[IMPORTANT]
====
The same provider requirements apply in plain Java, Spring Boot and Quarkus JVM applications:

* The `ConstraintProvider` class cannot be final or sealed.
* The `ConstraintProvider` class cannot declare final methods.
* The provider's class file must be available to its class loader.
* When a generated subclass is needed, the provider cannot implement `java.io.Serializable`.
* When a generated subclass is needed, a provider in a named Java module must open its package to the GreyCOS core module.

GreyCOS validates the provider and analyzes its bytecode while building the solver factory.
If analysis finds no eligible repeated lambdas or method references, the original provider class is used without transformation.
If a required transformation cannot be completed, solver creation fails with the provider name, cause and suggested remedy.
Unsupported bytecode and missing module access are errors; there is no fallback after a transformation failure.
====

For example, when both the application and GreyCOS use named modules, add this directive to the application's `module-info.java`:

[source,java,options="nowrap"]
----
opens org.acme.constraints to greycos.solver.core;
----

Alternatively, open the package at launch with `--add-opens my.application/org.acme.constraints=greycos.solver.core`.
If GreyCOS is on the class path, use `--add-opens my.application/org.acme.constraints=ALL-UNNAMED` instead.
Replace the module and package names with those reported in the startup exception.

==== Eligible lambdas and provider behavior

Automatic node sharing considers ordinary lambdas and method references that capture no values.
It compares the functional interface, method types and complete implementation information.
For lambda bodies that can be compared safely, this includes instruction operands, control flow, exception handlers,
typed constants and bootstrap arguments.
Method references retain the identity of their target method.
Matching source text alone does not establish equivalence, and a hash collision cannot make two implementations equivalent.

GreyCOS also checks available application helper methods for stack observation, following calls and method references
without initializing the helper classes.
Lambdas that capture stack traces, inspect the stack through helpers, or depend on helper bytecode that cannot be analyzed
retain their original implementation identity.
An unsafe lambda does not prevent unrelated eligible lambdas from sharing.
This analysis inspects available method declarations; it does not prove the behavior of every runtime override or reflective call.
Callbacks and their dynamically selected callees must not depend on the caller's stack.
If a constraint-building method selected for copying calls a stack-observing helper,
solver creation fails with the method and helper chain.

Lambdas that capture values, including `this`, remain unshared.
Lambdas using the extended lambda bootstrap, such as serializable lambdas or lambdas with additional marker interfaces,
also remain unshared.
Their captured values, serialization behavior and additional interfaces are preserved when other sites in the provider are shared.
The provider itself must be non-serializable when transformation is required:
Java object serialization cannot resolve hidden provider classes, including provider instances captured by serializable lambdas.
GreyCOS detects this condition at startup and reports how to change the provider or disable the feature.

GreyCOS generates a hidden subclass of the original provider in the same class loader, package and module,
with access to the original provider's private members.
Provider instances remain assignable to the configured provider class; `getClass()` returns the generated subclass.
Use the original class literal when code needs the configured provider's class identity.
The subclass delegates construction to the original constructors and keeps the original instance fields and static fields.
The original static initializer runs once, and existing static configuration remains visible.
Lambda implementation methods remain in the original class.
Each shared lambda is created and cached when its first original call site executes.
Concurrent access publishes one instance per group, using a separate lock for each group.
Calls from original constructors can initialize that group's lambda at its original point in construction.
Defining the generated class does not create the shared lambdas or initialize their functional interfaces early.
Private constraint-building helpers and superclass calls retain their receiver and dispatch behavior.
Ordinary method references to copied private or static helpers use bridges to those helpers,
so eligible stream operations inside them can share too.
Serializable and marker-interface references keep their original targets and serialization behavior;
they do not use these bridges.

Breakpoints in copied constraint-building methods may not bind to the hidden subclass.
Breakpoints in original constructors and lambda implementation methods can still apply, subject to debugger support.
Disable automatic node sharing when you need to step through the original constraint-building methods.

==== What is node sharing?

When using xref:constraints-and-score/score-calculation.adoc#constraintStreams[constraint streams], each xref:constraints-and-score/score-calculation.adoc#constraintStreamsBuildingBlocks[building block] forms a node in the score calculation network.
When two building blocks are functionally equivalent, they can share the same node in the network.
Sharing nodes allows the operation to be performed once for those building blocks, reducing repeated work during score calculation.
To be functionally equivalent, the following must be true:

* The building blocks must represent the same operation.

* The building blocks must have functionally equivalent parent building blocks.

* The building blocks must have functionally equivalent inputs.

For example, the building blocks below are functionally equivalent:

[source,java,options="nowrap"]
----
Predicate<Shift> predicate = shift -> shift.getEmployee().getName().equals("Ann");

var a = factory.forEach(Shift.class)
               .filter(predicate);

var b = factory.forEach(Shift.class)
               .filter(predicate);
----

Whereas these building blocks are not functionally equivalent:

[source,java,options="nowrap"]
----
Predicate<Shift> predicate1 = shift -> shift.getEmployee().getName().equals("Ann");
Predicate<Shift> predicate2 = shift -> shift.getEmployee().getName().equals("Bob");

// Different parents
var a = factory.forEach(Shift.class)
               .filter(predicate2);

var b = factory.forEach(Shift.class)
               .filter(predicate1)
               .filter(predicate2);

// Different operations
var a = factory.forEach(Shift.class)
               .ifExists(Employee.class);

var b = factory.forEach(Shift.class)
               .ifNotExists(Employee.class);

// Different inputs
var a = factory.forEach(Shift.class)
               .filter(predicate1);

var b = factory.forEach(Shift.class)
               .filter(predicate2);
----

Counterintuitively, the building blocks produced by these seemingly identical methods are not necessarily functionally equivalent:

[source,java,options="nowrap"]
----
UniConstraintStream<Shift> a(ConstraintFactory constraintFactory) {
    return constraintFactory.forEach(Shift.class)
                  .filter(shift -> shift.getEmployee().getName().equals("Ann"));
}

UniConstraintStream<Shift> b(ConstraintFactory constraintFactory) {
    return constraintFactory.forEach(Shift.class)
                  .filter(shift -> shift.getEmployee().getName().equals("Ann"));
}
----

The Java Virtual Machine is free to (and often does) create different instances of functionally equivalent lambdas.
Constraint Streams compare lambda instances, so separately created instances can prevent otherwise equivalent nodes from being shared.

When automatic node sharing finds eligible equivalent lambda sites,
the generated subclass uses a shared cached instance for those sites.
Consider the following input class:

[source,java,options="nowrap"]
----
public class MyConstraintProvider implements ConstraintProvider {

    public Constraint[] defineConstraints(ConstraintFactory constraintFactory) {
        return new Constraint[] {
            a(constraintFactory),
            b(constraintFactory)
        };
    }

    Constraint a(ConstraintFactory constraintFactory) {
        return constraintFactory.forEach(Shift.class)
                      .filter(shift -> shift.getEmployee().getName().equals("Ann"))
                      .penalize(SimpleScore.ONE)
                      .asConstraint("a");
    }

    Constraint b(ConstraintFactory constraintFactory) {
        return constraintFactory.forEach(Shift.class)
                      .filter(shift -> shift.getEmployee().getName().equals("Ann"))
                      .penalize(SimpleScore.ONE)
                      .asConstraint("b");
    }
}
----

The following simplified source illustrates the generated subclass.
The actual class is hidden, and its cached predicate calls the original lambda implementation:

[source,java,options="nowrap"]
----
class GeneratedConstraintProvider extends MyConstraintProvider {
    private static final Predicate<Shift> $predicate1 = shift -> shift.getEmployee().getName().equals("Ann");

    GeneratedConstraintProvider() {
        super();
    }

    @Override
    public Constraint[] defineConstraints(ConstraintFactory constraintFactory) {
        return new Constraint[] {
            a(constraintFactory),
            b(constraintFactory)
        };
    }

    @Override
    Constraint a(ConstraintFactory constraintFactory) {
        return constraintFactory.forEach(Shift.class)
                      .filter($predicate1)
                      .penalize(SimpleScore.ONE)
                      .asConstraint("a");
    }

    @Override
    Constraint b(ConstraintFactory constraintFactory) {
        return constraintFactory.forEach(Shift.class)
                      .filter($predicate1)
                      .penalize(SimpleScore.ONE)
                      .asConstraint("b");
    }
}
----

Both filters now receive the same predicate instance and have the same parent stream, so they can share one filter node.
This reduces repeated predicate evaluations.
It does not by itself establish a throughput or memory improvement; benchmark the enabled and disabled configurations on representative problems.


[#throttlingBestSolutionEvents]
=== Throttling best solution events in `SolverManager`

Throttling limits how often your consumer processes best solution events.
This reduces callback work when the solver improves solutions faster than your application needs updates.

To enable event throttling, use `withThrottledBestSolutionEventConsumer(...)`
when starting a new `SolverJob` using `SolverManager`:

[source,java,options="nowrap"]
----
...
import java.time.Duration;
...

public class TimetableService {

    private SolverManager<Timetable> solverManager;

    public String solve(Timetable problem) {
        String jobId = ...;
        solverManager.solveBuilder()
                .withProblemId(jobId)
                .withProblem(problem)
                .withThrottledBestSolutionEventConsumer(
                        event -> {
                           // Your custom event handling code goes here.
                        },
                        Duration.ofSeconds(1))
                .run(); // Start the solver job and listen to best solutions, with throttling.
        return jobId;
    }

}
----

During solving, this consumer receives at most one event per second.
Completion flushes the latest pending event immediately, so the final delivery may arrive sooner.

* The first event waits for the configured interval.
Updates replace the pending solution without postponing its delivery.
Continuous input therefore still produces periodic updates.
* Each job has independent throttling state, including jobs started from the same builder.
The job's event consumers run serially on its consumer thread.
A slow callback or an occupied thread can delay delivery.
* A problem-change future completes after a solution containing that change has been consumed.
Coalescing solutions retains the completion obligations for all changes they contain.
* A failed callback completes its associated problem-change futures exceptionally and invokes the configured exception handler.
The event is considered attempted, and later best solution events can still be delivered.
* Closing the manager drains accepted deliveries before releasing consumer resources.
If the closing thread is interrupted, cleanup still waits for callbacks to return and then restores the interrupt flag.
A close requested inside a callback returns before cleanup finishes; the pending delivery and cleanup follow that callback.

Throttling reduces consumer work. The solver still finds and clones best solutions and produces its normal internal events.

[NOTE]
====
When both a throttled best solution consumer and a final best solution consumer are configured,
the latest pending best solution is consumed before the final consumer runs.
An event already delivered to the best solution consumer is not delivered to it again during the flush.
====
