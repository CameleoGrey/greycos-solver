[#upgradeToLatest]
= Upgrading GreyCOS Solver
:doctype: book
:sectnums:
:icons: font

This page covers the API changes adopted from Timefold commits `5232c61..14249b7`.
GreyCOS keeps its own Maven coordinates, cotwin APIs, native threading, ALNS, islands and partitions.

[#automaticUpgradeToLatest]
== Automated migration

The migration artifact uses OpenRewrite to update Java source and Maven dependencies.
Run the following command with `GREYCOS_VERSION` set to the GreyCOS version you are adopting:

[source,shell]
----
mvn org.openrewrite.maven:rewrite-maven-plugin:6.46.1:run \
  -Drewrite.recipeArtifactCoordinates=io.github.cameleogrey:greycos-solver-migration:${GREYCOS_VERSION} \
  -Drewrite.activeRecipes=greycos.solver.migration.ToLatest
----

Review the resulting changes and compile and test your application.
The `greycos.solver.migration.ToLatest` entry point includes the existing migration recipes
and the preview API migration described below.
`greycos.solver.migration.PreviewToLatest` runs only the preview API migrations.
Kotlin source and the behavior changes in the next sections require manual updates.

[#manualUpgrade]
== Manual changes

=== Structural scores

Every built-in score has a leading `long structuralScore` record component.
Its value is `0` for a structurally sound solution and negative for a shadow variable dependency loop.
It is compared before all constraint score levels.
Existing score factory methods, ordinary constructors, and ordinary score strings remain valid.
A flawed score includes a prefix, such as `-1structural/0hard/-5soft`;
string-based Jackson, JAXB and JPA adapters use that representation.
Custom serializers must preserve the structural component too.

Record patterns need an additional leading component.
For example, `HardSoftScore(var hard, var soft)` becomes
`HardSoftScore(var structural, var hard, var soft)`.
`toLevelNumbers()` continues to return the constraint levels only.
Arithmetic methods construct ordinary scores and do not propagate structural state;
do not infer a solution's consistency by adding constraint totals.

Models with a `@ShadowVariablesInconsistent` field retain the legacy behavior:
inconsistent shadows become `null` and the marker is set to `true`.
Models without any such field use structural scores and reject inconsistent candidate solutions.
See xref:upgrading-greycos-solver/migration-guides/shadow-variables-inconsistent-to-structural-score.adoc[the migration steps]
and xref:constraints-and-score/overview.adoc#structuralScore[structural scores].

=== Neighborhoods preview API

The automated recipe renames `SamplingStream`, `UniSamplingStream` and `BiSamplingStream`
to `PickingStream`, `UniPickingStream` and `BiPickingStream` in the `stream.picking` package.
It also renames the corresponding internal stream types.

The following changes require manual updates:

* Build moves using `greycos.solver.core.preview.api.move.builtin.Moves` instead of importing concrete
  built-in move implementations. Those implementations moved into internal packages.
* Built-in move providers are final. Replace subclasses with a `MoveProvider` implementation
  or compose move streams in a `NeighborhoodProvider`.
* An explicitly constructed `ChangeMoveProvider` or `ListChangeMoveProvider` includes assignment
  and unassignment when its variable permits unassigned values. Pass `false` to the boolean
  constructor parameter to keep the old assigned-only behavior. The default provider set already
  passes `false` and adds separate assign/unassign providers.
* Keep using GreyCOS's cotwin metamodel types. Obtain the metamodel from the neighborhood builder
  or phase context; `SolutionView` does not expose `getSolutionMetaModel()`.

Configure `neighborhoodProviderClass` explicitly to enable Neighborhoods in GreyCOS.
Enabling the preview feature alone keeps the existing move selectors.
The new mass, pillar, subpillar, sublist, list-tail and 2-opt providers are described in
xref:optimization-algorithms/neighborhoods.adoc[Neighborhoods].

=== Custom list changes

Each `beforeListVariableChanged(entity, variableName, fromIndex, toIndex)` notification must
have a matching `afterListVariableChanged(...)` with the same `fromIndex`.
The ranges must cover every element inserted, removed or reordered.
Overlapping open changes for the same entity, duplicate closing notifications and mismatched
ranges now fail instead of corrupting undo state.
For example, appending one element uses `(size, size)` before the change and `(size, size + 1)` after it.
Use `MutableSolutionView` operations where possible so the solver manages these notifications.

=== Phase environment modes

A phase may select an environment mode at least as strict as its enclosing effective mode.
An unspecified mode inherits that mode, including within ALNS, island and partition configurations.
A solver using `NON_REPRODUCIBLE` cannot mix environment modes.
Benchmarks reject phase overrides, including nested ones, so each benchmark has one environment mode.
See xref:using-greycos-solver/running-the-solver.adoc#environmentModePerPhase[phase environment modes].

=== Metric tags

Solver metrics use the base tag keys `problem.id` and `island.id` in every execution scope.
Ordinary solves, manager jobs and benchmark runs use `island.id=root`;
child islands use their numeric island ID.
Benchmarks identify runs with `problem.id` instead of `greycos.benchmark.run`.
Update dashboards and filters that selected the former benchmark tag or expected no island tag.
