[#geneticAlgorithm]
= Genetic Algorithm

The genetic algorithm (GA) phase searches a population of assignment snapshots while retaining
working solutions for incremental scoring. It uses the application's normal `ConstraintProvider`
and native score ordering. The solver retains the best solution independently of population replacement.
GA is opt-in; the default construction heuristic and local search configuration is unchanged.

GA supports initialized solutions with basic planning variables, one planning list variable, or
both, using finite countable value ranges. Basic variables may belong to list owners, list elements,
or other planning entities. List values may be unassigned when the model permits it; all required
assignments must be initialized. By default, each GA phase runs serially, either standalone or inside an
asynchronous island model, including Java-configured nested islands. A standalone phase can enable
a bounded pool of parallel evaluators. GA cannot run under a
partitioned-search ancestor, and move workers must be disabled. Bounded offspring local improvement
is opt-in and requires serial evaluation.

[#geneticAlgorithmConfiguration]
== Configuration

Add a GA phase after construction, or supply a fully initialized input:

[source,xml]
----
<solver xmlns="https://github.com/CameleoGrey/greycos-solver/xsd/solver">
  <!-- solutionClass, entityClass and scoreDirectorFactory configuration -->
  <termination>
    <secondsSpentLimit>10</secondsSpentLimit>
  </termination>
  <constructionHeuristic/>
  <geneticAlgorithm>
    <termination>
      <moveCountLimit>10000</moveCountLimit>
    </termination>
    <populationSize>128</populationSize>
  </geneticAlgorithm>
  <localSearch/>
</solver>
----

The phase-local move limit gives the following local-search phase a chance to run within the global
time limit. Each completed seed or offspring attempt counts as one GA step and one move evaluation,
including cached duplicates, unchanged proposals and invalid proposals. With local improvement
enabled, each completed nested probe consumes an additional move evaluation, without creating a
GA step. The captured initial member does not consume an attempt. A score calculation is counted
only when it actually happens, including probe evaluation, accepted-move commit and recovery.

For a random starting solution, opt in to
xref:optimization-algorithms/construction-heuristics.adoc#randomAssignment[random assignment construction]:

[source,xml]
----
<constructionHeuristic>
  <moveThreadCount>NONE</moveThreadCount>
  <constructionHeuristicType>RANDOM_ASSIGNMENT</constructionHeuristicType>
</constructionHeuristic>
<geneticAlgorithm>
  <termination>
    <moveCountLimit>10000</moveCountLimit>
  </termination>
  <populationSize>128</populationSize>
  <moveThreadCount>NONE</moveThreadCount>
</geneticAlgorithm>
----

This construction phase produces one solution, replacing all movable input assignments while
preserving pins and list prefixes. It can replace an initialized input with a worse-scoring solution.
GA captures that solution as its first population member and performs its existing seeding for the
remaining members. Population size, mutation, crossover and evaluator settings keep their existing meanings.
The default construction heuristic is unchanged.

The corresponding Java GA phase configuration is:

[source,java]
----
new GeneticAlgorithmPhaseConfig()
        .withPopulationSize(128)
        .withCrossoverProbability(0.5)
        .withPBestRate(0.05)
        .withMutationRateMultiplier(0.0)
        .withTabuEntityRate(0.0)
        .withTerminationConfig(new TerminationConfig().withMoveCountLimit(10_000L));
----

[cols="2,1,4",options="header"]
|===
|Property |Default |Meaning
|`populationSize` |`128` |Positive number of population entries; duplicate assignments are permitted.
|`crossoverProbability` |`0.5` |Probability of applying the shared crossover to a parent pair; finite value in `[0, 1]`.
|`pBestRate` |`0.05` |Upper bound on the sampled ranked prefix or suffix fraction; finite value in `(0.000001, 1]`.
|`mutationRateMultiplier` |`0.0` |Finite nonnegative multiplier for mutation size. Zero still performs each operator's minimum mutation.
|`tabuEntityRate` |`0.0` |Finite rate in `[0, 1]` limiting recent selected positions within mutation groups.
|`migrationRate` |`0.00001` |Finite rate in `[0, 1]` controlling the number of population entries exchanged inside islands. Zero disables GA population exchange; the setting has no effect on standalone GA.
|`noProgressAttemptLimit` |`max(128, 10 * populationSize)` |Positive number of consecutive attempts without fresh valid offspring scoring before the phase exits.
|`localImprovementMoveCountLimit` |`0` |Nonnegative maximum number of local probes for each freshly scored generation child. Zero disables local improvement.
|`evaluatorThreadCount` |`0` |Nonnegative number of private evaluator workers. Zero retains serial execution; positive values enable a standalone pool without local improvement.
|`stepLoggingMode` |`ALL` |Log every completed attempt at `DEBUG`, or use `BEST_SCORE_IMPROVED` to log only attempts that strictly improve the owning solver's historical best score.
|`moveThreadCount` |Inherited |The effective setting must disable move workers. Set `NONE` on this phase to override a solver-wide setting.
|`mutationOperator` |All six equally |Optional named probabilities. An explicit list disables omitted operators.
|===

The no-progress limit counts lack of fresh valid scoring, not lack of a better best score.
It also bounds a population that repeatedly generates cached or unchanged proposals when the only
configured work limit counts score calculations. The phase logs its exit reason and work counters.

For example, enable only change and cyclic swap:

[source,xml]
----
<geneticAlgorithm>
  <mutationOperator>
    <type>CHANGE</type>
    <probability>0.75</probability>
  </mutationOperator>
  <mutationOperator>
    <type>SWAP</type>
    <probability>0.25</probability>
  </mutationOperator>
</geneticAlgorithm>
----

Each type may occur once. Probabilities must be finite and nonnegative, and their sum must be one.
At runtime, weights are renormalized over eligible operators; a group that is too small for an
operator does not make that operator applicable.

[#geneticAlgorithmStepLogging]
=== Step logging

With `DEBUG` enabled, the default `ALL` mode logs every completed seed or offspring attempt,
including duplicate, unchanged and invalid proposals. To log only completed attempts that strictly
improve the solver's historical best score, configure `BEST_SCORE_IMPROVED`:

[source,xml]
----
<geneticAlgorithm>
  <stepLoggingMode>BEST_SCORE_IMPROVED</stepLoggingMode>
</geneticAlgorithm>
----

The equivalent Java configuration is:

[source,java]
----
import greycos.solver.core.config.geneticalgorithm.GeneticAlgorithmPhaseConfig;
import greycos.solver.core.config.geneticalgorithm.GeneticAlgorithmStepLoggingMode;

var phaseConfig = new GeneticAlgorithmPhaseConfig()
        .withStepLoggingMode(GeneticAlgorithmStepLoggingMode.BEST_SCORE_IMPROVED);
----

This setting filters step messages; it does not enable logging. Enable `DEBUG` on the existing
phase logger or its parent package. For example, in `logback.xml`:

[source,xml]
----
<logger name="greycos.solver.core.impl.geneticalgorithm.DefaultGeneticAlgorithmPhase" level="debug"/>
----

The following illustrative output shows an improving attempt and a later non-improving attempt
in `ALL` mode:

[source,options="nowrap"]
----
DEBUG     Genetic Algorithm step (130), phase (1), generation (1), time spent (85), score (0hard/-40soft), new best score (0hard/-40soft), candidate score (0hard/-40soft), candidate (131), parents (8, 23), mutation (CHANGE, Task.machine), outcome (EVALUATED), admitted (true), changed (1).
DEBUG     Genetic Algorithm step (131), phase (1), generation (1), time spent (86), score (0hard/-70soft),     best score (0hard/-40soft), candidate score (0hard/-70soft), candidate (132), parents (8, 23), mutation (CHANGE, Task.machine), outcome (EVALUATED), admitted (false), changed (1).
----

`time spent` is elapsed solver time in milliseconds. `score` describes GA's current logical assignment;
with deferred pooled materialization, the coordinator graph may still contain an earlier assignment.
`candidate score` is reported separately because a cached duplicate leaves the logical assignment unchanged,
and an invalid candidate has no valid candidate score. The `new` marker means that the attempt
published a strict best-score improvement. Admission to the population alone does not imply improvement.

`BEST_SCORE_IMPROVED` omits the second line, equal scores, and improvements over the previous
workspace score that do not beat the historical best. Step indices retain their original values and
may have gaps. Set `ALL` explicitly to override an inherited filter. The filter also applies when
`TRACE` is enabled and works for serial and pooled evaluation.

Local improvement may publish several best solutions within one attempt. A completed attempt logs
one line with its final best score. Interrupted attempts and migration do not produce synthetic step
messages, even if they publish a best solution.
xref:optimization-algorithms/overview.adoc#SolverEventListener[`BestSolutionChangedEvent`] behavior
is unchanged; step logging is not a complete best-solution event stream. Inside islands, `best score`
belongs to the solver running that phase, and the line includes an `island (...)` suffix. It is not
necessarily the global best score; public solver events report only strict global improvements.
The filter changes neither search decisions nor events, metrics, or the existing `INFO` phase summary.

[#geneticAlgorithmStrategy]
== Selection, crossover and mutation

The initial input occupies the first population slot. Every remaining slot receives one independently
sampled assignment proposal. A valid proposal is admitted even if it duplicates another entry; an
invalid seed uses the initial member for that slot. There is no retry loop to force uniqueness.

At each generation, GA freezes the population in best-first native score order, breaking ties by
discovery identity. For each parent, it samples a fraction uniformly from `[0.000001, pBestRate)`,
rounds the corresponding prefix size upward, and samples a member uniformly from that best prefix.
It generates children in pairs and produces exactly `populationSize` offspring attempts per complete
generation; odd populations omit the unused second child.

The GreyJack source uses one crossover weight shared by all assignment positions. This retains or
exchanges the complete movable parent assignment before mutation, including all basic and list
assignments in a mixed model. Fixed assignments remain intact. Crossover does not combine arbitrary
list fragments. Mutation is attempted on every produced child regardless of whether crossover occurred.

Movable basic positions are grouped by entity type and planning-variable descriptor, in stable entity
encounter order. Pinned positions and singleton ranges do not participate. The phase first chooses
an eligible operator by its weight, then uniformly chooses one of that operator's eligible groups.

[cols="1,1,4",options="header"]
|===
|Type |Minimum group size |Operation
|`CHANGE` |1 |Independently sample each selected recipient's actual value range.
|`SWAP` |2 |Cyclically rotate values across selected positions.
|`SWAP_EDGES` |3 |Exchange selected adjacent edges, preserving the source's sequential behavior when edges overlap.
|`SCRAMBLE` |3 |Shuffle a contiguous segment of three to six positions, bounded by group size.
|`INSERTION` |2 |Remove one value and insert it at another selected position, shifting intervening assignments.
|`INVERSE` |2 |Reverse the interval between two selected positions.
|===

These intervals refer to the group's entity encounter order; they do not imply a planning list.
Permutation proposals are rejected as a whole if any transferred value is outside its recipient's
range. Recent selected positions are held in bounded tabu storage; old entries expire as necessary
to allow a mutation to select its required positions.

[#geneticAlgorithmListOperators]
=== List and mixed models

One additional mutation group contains all owners of the planning list descriptor. The same
configured operator weights apply to basic and list groups: select the eligible type first, then
uniformly select one eligible group. List eligibility is computed from the proposed child's current
lists. An operator cannot select a segment across an owner boundary or through a pinned prefix.

[cols="1,4",options="header"]
|===
|Type |List operation
|`CHANGE` |Relocate selected movable values, including unassigned ones, to compatible owners and insertion gaps. Include unassignment as a destination when allowed.
|`SWAP` |Cyclically rotate assigned values among selected unpinned positions, possibly on different owners.
|`SWAP_EDGES` |Sequentially exchange endpoints of actual adjacent pairs within unpinned suffixes. Selected edges may belong to different owners.
|`SCRAMBLE` |Shuffle a contiguous segment of three to six elements within one unpinned suffix.
|`INSERTION` |Relocate one assigned value within or between owners, preserving assigned membership.
|`INVERSE` |Reverse an interval within one unpinned suffix.
|===

For list seeding, copy fixed owner lists and pinned prefixes, shuffle the remaining canonical values,
then append each to a uniformly selected compatible movable owner. Allowed unassignment is one
additional destination. Entity-specific value ranges are honored. A required value with no legal
destination makes the proposal invalid; the ordinary initial-member fallback applies.

List mutation uses stable value identities for tabu storage, since positions change after transfers.
Its tenure is `ceil(tabuEntityRate * movableValueCount)`. Only selected anchors are recorded:
selected values for change and swap, edge starts for edge swaps, the segment start for scramble,
the moved value for insertion, and endpoints for inverse. Old anchors expire when needed to permit
selection. Change, swap and edge swaps retain the mutation multiplier and minimum-count rules;
the other operators retain their bounded selection sizes. Permutations outside recipient ranges
reject the whole proposal without score-guided repair or retries.

A configured portfolio with no eligible operation on the initialized input fails at startup when
movable assignments exist. If a later child has no eligible operation, mutation is skipped and the
child proceeds through normal evaluation. Its diagnostic mutation type is `NONE`; crossover may
still have changed the candidate. Normal attempt accounting and no-progress termination apply.

An owner's `@PlanningPin` freezes its complete list and basic variables. `@PlanningPinToIndex`
freezes only the prefix; a prefix ending at the current list size still permits appending. Pinning
a list element's basic variables does not pin its position in another entity's list. Conversely,
a fixed list position does not automatically pin the element's basic variables.

List snapshots use canonical phase-local element identities and require a value universe that fits
an integer-indexed array. They include values absent from current lists, including values available
only in pinned owners' ranges. Initial lists must contain the same object instances as the value
range; equal but distinct clones are rejected. Basic value ranges retain their existing long-indexed sampling.
Value ranges and pins remain stable during a phase and are recaptured after a problem-change restart.

For each child, GA samples an existing member from a randomly sized worst suffix of the frozen
population, using the same rank-fraction rule. Sampling is with replacement. The child wins if its
score is equal or better; otherwise the sampled existing member wins. Winners are buffered and
installed together after the entire generation completes. Duplicate entries can survive, and the
best population member can disappear. Best-solution publication therefore uses the solver's
independent best archive and does not insert an elite into the population.

This preserves the chosen GreyJack strategy with explicit GreyCOS adaptations: native score
ordering, the solver's seeded random generator, no unused child for odd populations, descriptor-based
groups and range validation, and no score calculation for a cached duplicate. It does not reproduce
GreyJack's entropy-seeded random trajectory.

[#geneticAlgorithmLocalImprovement]
=== Offspring local improvement

Set `localImprovementMoveCountLimit` to enable bounded improvement of generation children:

[source,xml]
----
<geneticAlgorithm>
  <localImprovementMoveCountLimit>32</localImprovementMoveCountLimit>
</geneticAlgorithm>
----

The Java equivalent is `new GeneticAlgorithmPhaseConfig().withLocalImprovementMoveCountLimit(32L)`.
The default is zero; negative limits fail at startup. With the feature disabled, the existing
population strategy and random trajectory remain unchanged. The value 32 is an example setting,
not a generally optimal tuning choice.

Improvement runs only after a generation child receives a fresh valid score. Initial population
capture, diversified seeding, cached duplicates, unchanged proposals and structurally invalid
proposals do not run local improvement. The child is already materialized in the retained scoring
workspace; improvement does not start another solver or rebuild the Bavet session.

Each probe chooses uniformly among the available move families: one basic value change, one list
relocation, or one list swap. Pure basic models have only value changes; list-only models have
relocation and swap; mixed models can use all three. Moves honor the current value ranges, pins,
list membership and allowed unassignment. A family that has no available move does not participate.
Basic changes sample a movable slot uniformly, then sample its finite value range. A selected
move that makes no change still consumes one probe and move credit, without a score calculation.
Temporary probes use normal notifications, shadow propagation, native scoring and undo. Only a
strictly better native score is accepted; equal scores are rejected. Accepted assignments and
their exact scores become the child's final genome and fitness for the existing replacement rule.

Every completed probe receives one move credit after its temporary state has been undone, even if
termination then prevents committing an improving probe. The accepted-probe counter advances only
after a change has been committed and its fresh score has been verified. The enclosing offspring
receives its separate move credit and GA step only when the attempt completes. Score-call limits
include actual scoring for the child, probes, accepted commits and restoration. A final rejected
temporary probe also requires a verified baseline score refresh before step metrics: undo queues
incremental scoring updates, and restoring the score field alone would leave them pending. Undo
and synchronization do not receive separate logical move credits. Consequently, a move limit
permits fewer offspring when local improvement is enabled.

Limits and cancellation are checked at safe probe boundaries. If a probe exhausts the remaining
budget or cancellation interrupts the attempt, GA restores the workspace state from before that
offspring attempt and discards the unfinished attempt and generation replacement buffer. Completed
probe credits, actual score calls and already published best improvements remain recorded.
The solver can therefore return a best solution discovered during an interrupted attempt, including
an improving probe published before termination prevented its commit. Accepted-probe counts can
include earlier completed commits from that same interrupted attempt.
If scoring or a listener throws, the phase aborts. Step metrics retain their last stable sample;
best metrics retain any valid best solution already published before the failure.

[#geneticAlgorithmIslands]
== GA inside islands

Each island owns its population, random stream, working solution and retained scoring session.
Place GA inside `islandModel` after initialization, or pass a fully initialized solution:

[source,xml]
----
<islandModel>
  <islandCount>4</islandCount>
  <migrationFrequency>10</migrationFrequency>
  <constructionHeuristic/>
  <geneticAlgorithm>
    <termination><moveCountLimit>10000</moveCountLimit></termination>
    <populationSize>128</populationSize>
    <migrationRate>0.00001</migrationRate>
    <moveThreadCount>NONE</moveThreadCount>
  </geneticAlgorithm>
</islandModel>
----

The `migrationFrequency` is measured in completed GA generations, excluding initial capture,
seeding and interrupted generations. Its public default remains `Integer.MAX_VALUE`; the value
`10` above is an example setting. Setting `migrationRate` to zero disables both sending and
receiving GA population batches. The rate does not affect standalone GA or its random trajectory.
The default `localImprovementMoveCountLimit` remains zero inside islands as well.

For a population of size `P` and positive migration rate, each exchange sends the best
`max(1, ceil(migrationRate * P))` population entries in native score order to the next island in
the ring. Exchange is asynchronous: a recipient consumes the latest complete available batch
at a safe generation boundary, and a newer complete batch can supersede an unread older batch.
There is no generation barrier across islands. The sender publishes detached assignment snapshots;
the receiver maps them to its own planning entities and values and scores them using notifications
through its own retained session. Migration requires stable planning IDs, value ranges and pinning
invariants. Invalid migration invariants abort the solve instead of becoming rejected offspring.

The recipient freezes its ranked worst entries before examining the batch, pairs them with the
ranked incoming entries, and replaces an entry only when the incoming native score is strictly
better. An equal score retains the resident entry. A migrant can improve the population even if
it is worse than the island's best archive. Duplicate population entries remain permitted.
Accepted replacements are committed together only after the complete batch has been processed;
GA does not rerank the population between individual pairs. Best improvements are published as
soon as they are scored, independently of admission. The next generation reranks the committed
population before selecting parents.

Migration creates no GA steps or move-evaluation credits and does not run offspring local
improvement. Actual receiver score calculations, including recovery, remain counted physical work.
If termination or cancellation interrupts a batch, the receiver restores and freshly verifies
its workspace from batch entry and discards all pending population replacements. Completed score
calculations and already published best improvements remain recorded. A fatal scoring, listener
or invariant failure aborts the phase; it is not treated as an ordinary rejected batch.

GA publishes improvements to the shared island best archive, but does not import that archive
into its population. `compareGlobalEnabled` and `receiveGlobalUpdateFrequency` continue to control
global-best adoption for local search and ALNS; they do not enable another GA migration path.
Enclosing island termination and score targets still observe GA's published improvements when
population exchange is disabled. Java configuration also permits GA inside nested islands, as
long as no enclosing phase is partitioned search. XML supports GA inside an island phase but
does not expose nested island phases.

Island scheduling and batch arrival order depend on thread execution. A fixed random seed does
not make asynchronous island runs reproduce a standalone serial trace. These rules establish
ownership, admission and accounting behavior; they do not establish a speedup or a search-quality
advantage. Compare island counts and migration settings on representative problems under matched
work and elapsed-time budgets, including runs with `migrationRate` set to zero.

[#geneticAlgorithmEvaluatorPool]
== Parallel evaluator pool

Set `evaluatorThreadCount` to evaluate generation offspring concurrently within one population:

[source,xml]
----
<geneticAlgorithm>
  <termination><moveCountLimit>10000</moveCountLimit></termination>
  <evaluatorThreadCount>4</evaluatorThreadCount>
  <moveThreadCount>NONE</moveThreadCount>
</geneticAlgorithm>
----

The Java equivalent is `new GeneticAlgorithmPhaseConfig().withEvaluatorThreadCount(4)`.
Null or zero preserves serial execution. A positive value creates that many evaluator workers in
addition to the coordinator thread. Population initialization and diversified seeding remain serial;
workers start only when generation work remains. The pool currently requires a standalone GA phase
with `localImprovementMoveCountLimit` equal to zero. Combining it with islands, partitioned search,
or enabled move workers fails before worker startup. The existing serial combinations remain available.

Each evaluator owns its working graph, score director, value ranges, shadows and retained scoring
session. Assignment records map to worker-local identities; mutable planning entities and list IDs
are never used directly across workspaces. Cloned objects require the normal lookup support used by
multithreaded solving, normally stable `@PlanningId` values. Non-immutable basic range values must
be canonical solution objects. Large finite numeric ranges do not need to be enumerated to transport
assignments. Problem facts shared by the normal solution cloner must
remain immutable during solving.

The coordinator selects parents, applies crossover and mutation, and consumes results in proposal
order. The number of outstanding attempts is bounded by the worker count, including completed
results waiting for earlier attempts. After committing the oldest attempt, the coordinator fills
the available pipeline capacity while other evaluations continue. It does not wait for every
attempt in the previous submission group to finish. Duplicate decisions still use the current
logical assignment, population and already selected generation winners. A proposal that depends
on an earlier unresolved proposal stops further preparation until that dependency is committed.
These barriers can temporarily limit concurrency. Population replacement still waits for a complete generation.

Pooled search uses a dedicated seeded proposal stream. With the same input, seed and deterministic
step or move limit, changing the evaluator count preserves the logical search decisions and final
assignments. Enabling the pool does not promise the existing serial random trajectory. Physical
score limits, elapsed-time limits and external cancellation can end at different logical prefixes.

Worker-native scores remain authoritative. Before publishing an improvement, the coordinator
materializes its genuine assignments and updates shadows through normal notifications, then uses
the standard predicted-score and best-solution lifecycle. It verifies and settles its retained score
state before sampling constraint totals, periodically, at generation boundaries and on normal or cancelled exit.
Assertion modes retain their additional score and shadow checks.

For list-only models in `NO_ASSERT`, the coordinator can defer materialization between these
observation points. It retains the genome and native score of the last fresh valid candidate as its
logical assignment, including a candidate rejected by survivor selection. Invalid, duplicate and
unchanged attempts leave that assignment intact. Step scores, change counts, duplicate detection
and survivor selection use this logical state. A predicted score is installed on the coordinator
solution only after its genuine assignments and shadows match.

Deferred materialization requires recognized framework termination conditions and no callbacks
that observe the working graph between publications. Basic or mixed models, assertion modes,
working-graph observers and unrecognized termination implementations retain eager coordinator
updates. Registering a lifecycle or committed-step observer during a run materializes the current
logical assignment and keeps subsequent attempts eager for that invocation. Best-solution event
listeners do not disable deferral: the corresponding assignment is materialized before publication.
Constraint-total metrics synchronize through their sampling hook. These choices do not change
the configured genetic operators, population rules or proposal random stream.

All completed worker score calculations count toward solver-wide and phase-local score limits,
including worker initialization, recovery and results discarded after termination. Coordinator
verification also counts. Only completed logical attempts receive GA step and move credits.
Score and time limits are cooperative targets: work already in flight and required cleanup can
cross them. Cancellation stops submissions and joins workers before normal phase completion.
An unfinished generation does not replace the population; already published best solutions remain
available. A worker that fails to stop prevents unsafe reuse of the same solver.

Parallel evaluation adds worker initialization, assignment transport and thread coordination.
Genetic operators, ordered commitment and population administration remain serial, and eager
observation requires additional coordinator updates. It can cost more than serial evaluation on
inexpensive constraints or duplicate-heavy populations. Compare complete search quality and
resource use on representative models; worker count alone does not establish speedup or linear scaling.

Internal phase diagnostics expose completed attempts, freshly evaluated offspring, seeding time,
search-invocation time, pooled coordinator materializations, whether deferral was used and the
eager fallback reason. Search-invocation time includes seeding and evaluator startup and shutdown;
the materialization counter excludes serial evaluation and seeding. Pool diagnostics separately
report worker submissions, completed evaluations, consumed results, retained sessions and physical
score calculations. For timing comparisons, collect these counters after solving: attaching a
working-graph lifecycle recorder selects eager execution and changes the path being measured.

[#geneticAlgorithmIncrementalScoring]
== Incremental scoring and lifecycle

Population genomes contain immutable genuine-assignment arrays and exact cached scores. They do
not contain separately editable shadows or cloned mutable working entities. Basic assignments use
normal value equality; ordered list snapshots use canonical element identities. Immutable list
snapshots can be shared by genomes and evaluator requests. Duplicate and diversity indexes use
only their immutable list fingerprint to select a bucket, then perform exact genome equality checks.
Basic values retain their live equality semantics and are never used as cached hash keys. The evaluator
validates the complete mixed candidate before any notification, then applies only changed basics
and differing list intervals. It brackets all affected owners together and emits membership events
only when values become assigned or unassigned. Transfers between owners remain assigned. Shadows
update after the complete delta, and scoring follows the standard phase scoring path.

With Bavet, this retains the existing working object graph and scoring session across offspring.
Replacing the entire working solution for every child would rebuild that session. Reusing a
score-director factory alone would not provide the same incremental behavior.

A valid child remains the logical assignment even when population replacement rejects it. Serial
and eager pooled execution also leave it materialized; deferred pooled execution may install it
later. A cached child does not need to be materialized or scored; its fitness is separate from the
current logical assignment's score.
A completed structural-invalidity result restores the previous genuine assignments through
notifications, updates shadows, recalculates the score and verifies restoration. Setter, listener,
scoring and callback exceptions abort the phase instead of being counted as rejected offspring.

Best improvements are published before population replacement. If termination interrupts a
generation, unfinished replacement buffers are discarded and already published improvements remain
available. Problem-change restarts and solver reuse reconstruct the population, cached fitness,
range mappings and mutation state. Normal phase transitions may rebuild working scoring state.

Standard step and score statistics remain available. GA phase and step diagnostics additionally
identify generation, population diversity, parent and replacement member identities, mutation type
and group, attempt outcome, admission, and changed assignments. The change count adds changed basic
slots and list values whose owner or index changed, including shifted suffixes. A cached attempt's workspace score
can differ from its candidate fitness; interpret those fields separately.
Phase diagnostics also count completed local-improvement probes and accepted probes, including
completed probes belonging to an interrupted offspring attempt.

Session retention establishes incremental evaluation, but does not establish a speedup. Broad
assignment changes can affect many constraints, and genome construction, diffing, cloning a new
published best, and population maintenance also consume resources. Benchmark representative models
against serial local search and applicable ALNS under matched starts and budgets.

[#geneticAlgorithmExample]
== Runnable example and evidence harness

Core test sources contain `greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmExample`.
It assigns tasks to machines with hard capacity limits and soft load-balancing and preference costs.
Its plain Java replay validates task and machine identities, immutable input data, complete assignments
and both score levels without calling Constraint Streams. The example exports assignments by stable
business ID, reloads them into a fresh model, and checks assignment equality and replayed score.

After building the project and compiling its test sources, run from the repository root:

[source,shell]
----
./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmExample \
  -Dexec.args="80 37 2000 target/genetic-algorithm/assignments.csv 32"
----

Arguments are task count, random seed, total move limit, output file and an optional per-child
local-improvement probe limit. Omitting the fifth argument retains the original zero limit.
The total move limit includes both completed offspring attempts and nested probes.

The bounded `GeneticAlgorithmBenchmark` harness first verifies every evaluator result against
independent business replay. It then compares full working-solution replacement with retained deltas
on the same pregenerated sparse and broad assignment sequences. Both measured evaluators calculate
every candidate, isolating the evaluation mechanism from the GA fitness cache. It verifies exactly
one retained session and one new session per full replacement.

The search comparison runs GA, GA with 32 local probes per child (`GA_LOCAL`), serial Late Acceptance
local search and basic-variable ALNS from
the same initialized assignments, with the same prescribed seeds and no move workers. Separate runs
use a physical score-calculation threshold and a wall-clock limit. Thresholds may be crossed at
different algorithm boundaries; the report includes actual work and time rather than treating the
configured threshold as exact equality. A 60-second fallback bounds each fixed-work run. No-progress
exit can stop GA earlier.

[source,shell]
----
./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmBenchmark \
  -Dexec.args="80 256 500 2000 11,37,83 target/genetic-algorithm/benchmark"
----

Arguments specify task count, evaluator candidate count, search milliseconds, search score-call
threshold, comma-separated seeds and output directory. `results.csv` records correctness,
completeness, feasibility, exact scores, score calls, session counts, assignment distance, setup and
work time, thread allocation, garbage collection, completed local probes and accepted local probes.
`metadata.properties` records JVM, heap,
processor, source revision and dirty status, warmup, termination and counter definitions. Search results also export assignment files
and independently verify their reloads. Evaluator ordering alternates explicitly between full
replacement first and retained deltas first by seed and shape. Search order rotates by seed and
reverses for the second budget kind; no random shuffle determines execution order.

The `greycos.gaBenchmark.reverseOrder=true` JVM property reverses these orders for a paired run.
`greycos.gaBenchmark.orderOffset` shifts the seed/model order index. For focused fresh-JVM runs,
`greycos.gaBenchmark.algorithms` selects a comma-separated subset of `GA,GA_LOCAL,LS,ALNS`
(`GA_PLUS_LOCAL` is an alias for `GA_LOCAL`), `greycos.gaBenchmark.budgets` selects `score_calls`
or `milliseconds`, and `greycos.gaBenchmark.skipEvaluators=true` skips evaluator comparisons.
Each selected search still receives its own 200-score-call warmup solve. These optional properties
do not change the existing six positional arguments or the solver's configuration defaults.

Every search row also reports time to the same prespecified target: a feasible solution whose soft
penalty is at most the theoretical balanced integer load penalty plus half the initial preference
penalty. The threshold comes only from the input, before search. Time is zero when the initialized
input already meets it, otherwise the first matching best-solution event is recorded; `unreached`
and `-1` distinguish a missed target from a measured success. The target need not be achievable.
For a dirty checkout, retain the qualification diff with the report; the HEAD revision alone does
not identify uncommitted changes. The `greycos.gaBenchmark.revision` system property can provide an
external exact revision identifier.

Evaluator session counts are exact and include initial setup. Search session counts observe
distinct sessions at phase and completed-step boundaries; they do not instrument every session
constructor. Evaluator assignment distance is the sum between successive candidates; search
distance compares the initial and returned best assignments. Allocation uses the current thread's
JVM counter, or `-1` where unsupported. Verification and export happen outside measured work time.

The harness is bounded evidence, not a statistical performance qualification. It does not assert
timing thresholds, prove optimality, or justify a general speedup claim. Larger studies need multiple
fresh JVM runs, representative instances, held-out seeds, sufficient warmup, and separate assessment
of feasibility, solution quality, resource use and setup cost.

[#geneticAlgorithmListExamples]
=== List and mixed examples

`GeneticAlgorithmListExample` sequences tasks on machines. Hard penalties measure capacity excess;
soft costs measure position-weighted processing time and setup between adjacent task families.
`GeneticAlgorithmMixedExample` uses a separate mixed model in which each task also selects a
processing mode that changes its duration and incurs a mode cost. Both use the same solver-free
business records and arithmetic replay, and neither relies on Constraint Streams to validate the
business result.

The examples validate canonical task and machine identities, immutable input data, exact list
membership and order, processing modes, and derived owner/index state. Versioned CSV exports use
stable business IDs and an input fingerprint. Reload constructs a fresh model and verifies exact
assignments and the independently replayed score.

After compiling the core test sources, run either example:

[source,shell]
----
./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmListExample \
  -Dexec.args="80 37 2000 target/genetic-algorithm/stage3/list.csv 32"

./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmMixedExample \
  -Dexec.args="80 37 2000 target/genetic-algorithm/stage3/mixed.csv 32"
----

Arguments are task count, random seed, physical score-call limit, output file, and an optional
local-improvement probe limit per child. Omitting the fifth argument retains the original zero
limit. A score-call
threshold is checked at solver boundaries; actual work may exceed it. Both examples report required
completeness, feasibility, score, and replay separately.

`GeneticAlgorithmListBenchmark` runs both models. It compares retained deltas and full replacement
on identical sparse and broad candidate sequences, then compares GA, GA with local improvement,
serial Late Acceptance, and
ALNS from matched initialized assignments. It uses the same seeds, separate score-call and wall-clock
budgets, and a 60-second fallback for work-limited searches. The prespecified quality target is a
feasible score whose soft penalty is at most 90 percent of the initial penalty. Missed targets remain
explicitly unreached.

[source,shell]
----
./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmListBenchmark \
  -Dexec.args="80 256 500 2000 11,37,83 target/genetic-algorithm/stage3/benchmark-80"
----

Repeat with task counts 256 and 1,024 and then run the matrix in fresh JVMs with
`greycos.gaBenchmark.reverseOrder=true` to counterbalance execution order. Arguments use
the same order as the basic-variable benchmark. The CSV includes actual scores, resource use,
physical score calls, session counts, assignment distance, changed lists, local probe/acceptance
counts, and replay status. `greycos.gaBenchmark.models=list_only` or `mixed` selects one model;
both run by default. Evaluator ordering also alternates by model, and search ordering rotates by
model in addition to seed.
Evaluator distances and changed-list counts accumulate consecutive transitions; search distances
compare the initialized input with the returned best. Session counts are exact for evaluator runs
and observed at phase/step boundaries for searches. Independent replay and export are outside
measured work. These are bounded workload observations; session retention alone establishes no
speedup, feasibility-discovery capability, or general search-quality advantage.

The 2026-10-08 qualification measured the 32-probe setting on the basic, list-only and mixed fixtures
at 80, 256 and 1,024 tasks, seeds 11, 37 and 83, and separate 2,000-score-call and 500 ms limits.
Across two counterbalanced repetitions in 12 fresh JVMs, GA with local improvement returned a worse
final score than plain GA in all 108 paired comparisons (54 distinct cases repeated twice).
All 432 search results passed replay and export/reload and remained complete and feasible from
feasible starts. This establishes neither feasibility discovery nor optimality. The tested
32-probe setting is not qualified as a beneficial default; local improvement remains opt-in with
default zero. Evaluate other limits on representative workloads before enabling it.

[#geneticAlgorithmEvaluatorExample]
=== Evaluator pool example and comparisons

`GeneticAlgorithmEvaluatorExample` runs standalone pooled GA on the same basic, list-only or mixed
business models. It independently replays the returned solution and checks exact export/reload:

[source,shell]
----
./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmEvaluatorExample \
  -Dexec.args="mixed 80 37 20000 target/genetic-algorithm/stage4b/mixed.csv 4"
----

Arguments are model (`basic`, `list_only` or `mixed`), task count, seed, physical score-call target,
output file and evaluator worker count. The target includes worker initialization and coordinator
verification, and actual work can exceed it through cooperative termination.

`GeneticAlgorithmEvaluatorBenchmark` compares serial GA, one/two/four evaluator workers, serial
Late Acceptance and ALNS, and GA/LA islands with matching worker counts. Pool and island variants
include one coordinator in their declared thread allocation. It also compares full replacement,
retained serial deltas and the production pool on identical sparse and broad candidate sequences.
Untimed correctness passes verify actual evaluated assignments against independent business replay.

[source,shell]
----
./mvnw -pl core exec:java \
  -Dexec.classpathScope=test \
  -Dexec.mainClass=greycos.solver.core.impl.geneticalgorithm.GeneticAlgorithmEvaluatorBenchmark \
  -Dexec.args="mixed 80 2000 20000 11,37,83 target/genetic-algorithm/stage4b/benchmark-80"
----

`results.csv` records whole-search quality, actual physical work, replay status, setup and cleanup,
process CPU, all-thread allocation, garbage collection and worker diagnostics. `evaluator-results.csv`
isolates the fixed candidate sequences. Session counts identify their observation scope and exclude
temporary assertion directors. The metadata describes budget, warmup, execution order and resource
accounting. Repeat all three models at sizes 80, 256 and 1,024 in fresh JVMs with opposite execution
orders before interpreting performance. These measurements do not establish general speedup,
optimality or feasibility discovery from the feasible example starts.
