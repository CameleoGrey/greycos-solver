[#guidedLocalSearch]
= Guided Local Search

Guided Local Search (GLS) changes the search objective when ordinary improvement stalls.
By default, it derives features from planning assignments and directed list relationships,
then estimates their costs from evaluated moves.
Applications can also supply features with objective-specific costs.
GLS increases penalties on selected costly features so that subsequent moves favor alternatives.
These penalties guide move selection; the planning score, retained best solution, score explanations,
and score-based termination continue to use the original constraints.

GLS runs inside a local-search phase with a dedicated decider.
It requires an initialized solution; the construction heuristic's result may still be infeasible.
It supports basic and list planning variables, incremental score calculation, move workers, and islands.
Benchmark it against existing search configurations on representative inputs before choosing it for production.

[#guidedLocalSearchObjective]
== Search objective and penalty updates

GreyCOS maximizes scores. In the default `ALL_LEVELS` guidance mode, GLS maintains a separate penalty history
for each business score level. It guides one level `k` at a time:

[source,text]
----
penalty[k](x) = penaltyFactor * sum(penaltyCount[i, k] * cost[i, k](x))
guidedLevel(x) = originalLevel[k](x) - penalty[k](x)
utility(i, k) = cost[i, k](x) / (1 + penaltyCount[i, k])
----

The sum includes the configured automatic and custom feature families.
Each feature starts with a zero penalty count at every level.
After a complete round with admissible candidates but no accepted move, GLS updates costs and penalties,
then starts another round under the new guidance.
Only active, positive-cost features tied for maximum utility can receive a penalty increment.
If `M` features have positive cost and `T` share maximum utility, the update increments
`min(T, ceil(M / 16))` distinct features.
Selection uses stable feature order and the coordinator's seeded random generator.
For example, a 2,024-way initial tie increments 127 features.

Features no longer present retain their penalty counts for future appearances.
Counts do not decay. By default, discovering a new original-score best does not clear them.
A penalty update does not itself accept a move: every committed search move must improve the guided comparison
or improve the retained original-score best through _aspiration_, while satisfying the current admission rules.
Equal guided comparisons do not count as improvement.

The guided comparison first preserves structural validity and mandatory initialization.
It compares the original score levels above `k`, the guided level at `k`, and the original levels below `k`,
in that order. Original-score aspiration is also subject to structural, initialization, protected-prefix,
and controller-state admission rules.
A candidate that merely improves the current original score receives no aspiration unless it beats the retained best.

All sixteen built-in integral, decimal, float, and double score types are supported, including bendable scores.
The target index is zero-based over business score levels; it excludes structural and initialization components.
Penalty factors, feature costs, comparisons, medians, and utility ties use exact rational arithmetic.
Fractional penalties remain significant even for integral scores.
For example, factor `0.1`, count `1`, and cost `3` contribute `0.3` to guidance.

=== Automatic features and learned costs

For basic variables, a feature identifies the entity, variable, and assigned value.
For list variables, the default features identify directed adjacency and owner-specific start and end boundaries.
Set `automaticListOwnershipEnabled` to `true` to additionally identify each value's assigned owner.
Unassigned values use distinct tokens where unassignment is allowed.
Pinned assignments and immutable prefix interiors are omitted; mutable boundaries remain available.
Mixed models combine these features. Single-threaded GLS adds no `@PlanningId` requirement;
move workers retain the usual lookup and rebasing requirements.

GLS learns an estimated cost for each automatic feature and score level from temporary candidate evaluations.
Let `R` be the automatic features removed by a candidate and `A` those added, after canceling transient changes:

[source,text]
----
d = max(size(R), size(A))
z[k] = (candidateLevel[k] - incumbentLevel[k]) / d
observation[i, k] = +z[k] for i in R, -z[k] for i in A
weight[i, k] = clamp(4 + trunc(4 * medianObservation[i, k] / scale[k]), 1, 16)
cost[i, k] = scale[k] * weight[i, k] / 4
----

A candidate with `d = 0` supplies no cost observation but still advances the event history.
Otherwise, removing a feature when the score improves raises its estimated cost;
adding a feature in the same situation lowers its estimated cost.
The observations are a heuristic attribution of the move's score change, not a decomposition of the constraints.

The observation history covers the last 256 valid, coordinator-consumed candidate events.
Each feature uses at most its latest eight observations within that history, including zero observations.
The median of an even number of observations is the arithmetic mean of its middle two values;
`trunc` truncates toward zero. A feature without an estimate starts with weight `4`.
At a penalty barrier, features with new observations update their weights.
Published weights remain available when their observations expire and no new observation replaces them.
Histories for features that are neither active nor penalized at any level are discarded at publication.
Custom feature costs come directly from the provider and are not learned or rescaled.

Each level has a separate rolling scale history of at most 256 eligible, nonzero values of `abs(z[k])`.
Without directed origin selection, every valid consumed candidate is eligible.
With directed selection, only candidates drawn ordinarily from the origin source calibrate the scale;
both ordinary and directed candidates supply feature-cost observations.
The scale starts provisionally at one. Its first empirical median replaces that provisional value directly.
Later empirical updates are clamped to between half and twice the previously published scale.
A positive `levelScale` override fixes that level's scale and bypasses calibration.
It does not disable automatic feature learning.

Learning consumes only structurally valid, fully initialized results used by the coordinator, in candidate order,
including candidates subsequently rejected by score or controller admission rules.
Discarded speculative worker results do not contribute observations.
Costs and scales are published at penalty-update barriers and remain frozen throughout each candidate round.
The tracker exports changed feature keys without extracting all features for every candidate.
Learning uses existing score evaluations and does not depend on constraint matches or add score calculations.

[#guidedLocalSearchRounds]
== Focus, bounded excursions, and neighborhood coverage

`ALL_LEVELS` begins with the first negative hard level, or the last business level when the solution is feasible.
A focus epoch permits at most `focusStepLimit` committed moves or `focusPenaltyUpdateLimit` penalty updates,
with defaults of 64 and 8.
If a committed solution improved the original-score prefix through the focused level relative to the epoch's start,
the next epoch retains that focus.
A stagnant epoch moves to the preceding level without cyclic wrapping; productive soft descent is not interrupted
merely because 64 moves have completed.
Penalty histories survive focus changes.

Ordinary search protects the original hard-score vector lexicographically and the original prefix above the active focus.
Ordinary search and repair also reject a feasible-to-infeasible transition, even if it improves the hard vector lexicographically.
Original-best aspiration remains subject to this admission rule.
Stagnation that reaches hard guidance, including a stagnant initial hard focus, starts a deliberate excursion.
During that excursion, guided improvements may worsen the focused hard level while preserving its earlier prefix.
The excursion permits at most `excursionStepLimit` committed moves, eight by default.
If it has not recovered feasibility, GLS enters repair with at most `excursionRepairStepLimit` further committed moves,
64 by default. Repair does not allow the original hard score to worsen.
Partial hard-score improvements do not restart that repair budget.
In `ALL_LEVELS`, repair focuses on the first violated hard level.
An excursion that becomes feasible again immediately returns to ordinary search at the last business level.
An excursion that remains feasible also returns there when its move budget ends.
If repair cannot find a move or exhausts its budget, the phase ends with an explicit repair-exhaustion reason.
GLS retains the best original score, including while the working solution is infeasible.
Once a feasible solution has been found, the returned best remains feasible if the score model orders every feasible solution
above every infeasible solution, as the routing and cloud examples' penalty models do.
A model with positive hard rewards can violate this assumption: the hard vector `[1, -1]` is infeasible
yet lexicographically better than the feasible vector `[0, 0]`.
Retained-best selection follows that native score ordering.

`FIXED_TARGET` guides `targetScoreLevelIndex`, the last level by default, and never changes that target.
It protects the original prefix above the target and uses the same bounded retry policy.
A fixed hard target can use the excursion and repair policy without rotating to another target.
An explicit target with no guidance mode selects `FIXED_TARGET` for compatibility.
Specifying both `ALL_LEVELS` and a fixed target is invalid.
GLS is a heuristic; bounded excursions do not guarantee feasibility or optimality.

[cols="1,3",options="header"]
|===
|Search mode |Meaning of a completed unsuccessful round
|`SAMPLED` (default)
|No accepted improvement appeared in at most `sampleSize` attempted candidates.
This is sampled stagnation, not evidence of a local optimum.
Random, nearby, and k-opt selectors require this mode.
|`EXHAUSTIVE`
|No accepted improvement appeared during complete enumeration of the configured supported neighborhood.
The result is local optimality relative to that neighborhood, the frozen guided objective, and the current admission rules.
|===

`sampleSize` counts attempted candidates, including moves that cannot be executed.
It is independent of the ordinary forager's `acceptedCountLimit`.
After an unsuccessful round with admissible candidates, GLS retries under new penalties;
it does not force an arbitrary escape move.
`maxPenaltyUpdatesPerStep` bounds these updates across all focuses in one decision, with a default of 64.
Exhaustion ends the phase normally with `GUIDED_RETRY_EXHAUSTED`, including under step-count-only termination.
This bound also applies when positive-cost features are constant and cannot change candidate ranking.

`maxUnproductiveRounds` counts consecutive sampled rounds with no admissible candidate.
Reaching this bound can escalate an ordinary `ALL_LEVELS` focus if valid, fully initialized candidates were encountered.
A fixed hard target can enter an excursion if a candidate respects its protected prefix.
If no such transition is available, the phase ends.
Exhaustive mode makes the same decision after one complete round.
An empty neighborhood or fixed-target prefix violations do not trigger an escape.

When an admissible round has no positive-cost feature to penalize, `ALL_LEVELS` checks preceding focuses down to zero,
without wrapping, and can enter or continue a hard excursion during that bounded search.
`FIXED_TARGET` and repair check only their current target.
The phase ends if no eligible feature is found; failure during repair reports `EXCURSION_REPAIR_EXHAUSTED`.
Termination is checked throughout candidate and penalty rounds.
Penalty updates do not create moves, completed steps, best-solution events, or score calculations.
A step-count limit counts committed moves.

Exhaustive mode accepts explicit `ORIGINAL` change or swap selectors for basic variables,
list-change or list-swap selectors for list variables, and unions of those selectors.
It rejects random and nearby selection, k-opt, selected-count truncation, custom selectors,
and Neighborhoods repositories. A count-limited random iterator does not enumerate a neighborhood,
even though its iterator ends.

=== Directed origin selection

`directedOriginSelection=true` prefers move origins associated with high automatic penalty pressure
before the selected move is built.
It uses tournaments of at most eight eligible origins, with every fourth selection requesting ordinary exploration.
Finite origin streams use a bounded buffer to reorder selections, retaining every source selection once.
Without active penalty pressure, selection remains ordinary.
An ordinary slot draws a fresh origin directly from the source while any remain, including when the buffer contains
tournament candidates. Any final buffered origins are emitted without contributing to scale calibration.
Existing filters, pins, value ranges, mimic relationships, and nearby selection remain effective.
An ordinary exploration slot still obeys the configured nearby restriction;
include an unrestricted branch when broad exploration is wanted.

This option supports just-in-time change, swap, list-change, list-swap, sublist-change, sublist-swap,
and k-opt selectors, and supported unions of those selectors.
Unsupported custom selectors, Neighborhoods repositories, exhaustive mode, cached move trees,
and unsupported selector combinations fail during solver construction with the selector path and remediation.
Set `directedOriginSelection=false` to use such neighborhoods with the same GLS learning and controller.
The library default is `false`; the routing examples enable it explicitly.
Automatic feature composition is required for origin priorities; opaque custom keys still affect evaluated guidance
when `featureComposition=COMBINED`.

[#guidedLocalSearchConfiguration]
== Configuration

Set the local-search type to `GUIDED_LOCAL_SEARCH` to use automatic features across all score levels.
An optional feature-provider class must have a public no-argument constructor.
GLS owns acceptance and move selection; do not combine it with an `acceptor` or `forager` configuration.
Automatic benchmark blueprints can use GLS without application-specific configuration.

Feature composition is resolved as follows:

[cols="2,2,3",options="header"]
|===
|`featureComposition` |Feature families |Provider requirement
|`AUTOMATIC` |Automatic features only |Do not specify a provider. Supports both guidance modes.
|`CUSTOM` |Provider features only |Provider required. Omit `levelScale`; leave ownership and directed selection disabled.
|`COMBINED` |Automatic and provider features |Provider required. Families have separate key spaces.
|Omitted, `ALL_LEVELS` |Automatic without a provider; combined with a provider |Retains the previous resolution rule.
|Omitted, `FIXED_TARGET` |Custom features |Provider required. Set `AUTOMATIC` explicitly for an automatic fixed target.
|===

[cols="2,1,3",options="header"]
|===
|Property |Default |Meaning
|`guidanceMode` |`ALL_LEVELS` |Adapt focus on stagnation; `FIXED_TARGET` keeps one target. An explicit target without a mode selects `FIXED_TARGET`.
|`featureProviderClass` |None |Custom feature provider used by `CUSTOM` and `COMBINED`.
|`featureComposition` |Resolved above |Select automatic, custom, or combined features.
|`automaticListOwnershipEnabled` |`false` |Add list ownership to automatic adjacency and boundary features.
|`directedOriginSelection` |`false` |Prefer penalized origins in supported sampled selector trees.
|`penaltyFactor` |`0.1` |Strictly positive decimal multiplier applied to feature penalties.
|`targetScoreLevelIndex` |Last level in fixed mode |Zero-based fixed target; cannot be combined with `ALL_LEVELS`.
|`focusStepLimit` |`64` |Maximum committed moves in one focus epoch. Progress renews the same focus.
|`focusPenaltyUpdateLimit` |`8` |Maximum penalty updates in one focus epoch. Stagnation can escalate focus.
|`maxPenaltyUpdatesPerStep` |`64` |Maximum penalty updates across focuses before a decision ends without a move.
|`excursionStepLimit` |`8` |Maximum committed moves in a deliberate hard-score excursion.
|`excursionRepairStepLimit` |`64` |Maximum subsequent committed repair moves; partial repair does not renew the budget.
|`levelScale` |Rolling calibration |Repeatable `scoreLevelIndex` and positive fixed `scale` for automatic features.
|`searchMode` |`SAMPLED` |Sampled stagnation or supported exhaustive enumeration.
|`sampleSize` |`1000` |Maximum attempted candidates per sampled round. Omit in exhaustive mode.
|`maxUnproductiveRounds` |`3` |Consecutive sampled rounds allowed without an admissible candidate.
|`resetPenaltiesOnNewBest` |`false` |Clear penalty counts after a new original-score best.
|===

Omitted configuration fields stay unset through copying, inheritance, XML serialization, and native configuration generation.
Defaults are resolved when the solver is built.
Existing explicit sample sizes, factors, scale overrides, targets, and reset settings remain effective.
For changed search behavior, see the xref:upgrading-greycos-solver/upgrade-to-latest.adoc#guidedLocalSearchUpgrade[GLS upgrade notes].

[#guidedLocalSearchFeatureProvider]
== Implementing a feature provider

Implement the public APIs in `greycos.solver.core.api.localsearch`:

[cols="2,3",options="header"]
|===
|Interface |Responsibility
|`GuidedLocalSearchFeatureProvider<Solution_, Key_>`
|`extractFeatures` independently enumerates the features of a solution; `newSession` creates private incremental state.
|`GuidedLocalSearchFeatureConsumer<Key_>`
|`accept(key, longCost)`, `accept(key, BigDecimalCost)`, `acceptFloat`, and `acceptDouble` emit scalar costs; `acceptScore` emits per-level costs.
|`GuidedLocalSearchFeatureUpdater<Key_>`
|The consumer operations insert or replace a feature; `remove(key)` removes its presence.
|`GuidedLocalSearchFeatureSession<Solution_, Key_>`
|Resets against a working solution, receives variable notifications, flushes changed features, and closes its resources.
|===

Keys must be non-null, immutable, and equal across cloned solutions.
Use immutable business IDs or records composed of those IDs; do not use a mutable planning entity as a key.
Each key represents binary feature presence. If the same kind of feature occurs several times,
give each occurrence a distinct key. Full extraction must emit each key once.
Costs must be finite and nonnegative. Zero-cost features may be present but are never selected for penalty increments.
Changing a present feature's cost keeps its penalty count.
An incremental `remove` must name a currently present feature.

Choose features whose removal or replacement describes useful alternative decisions.
They may represent only selected terms of the objective; their sum need not reproduce the whole business score.
Avoid including known immutable features: repeatedly penalizing a feature that no move can remove cannot guide useful choices.
Scalar costs apply to the last business level in `ALL_LEVELS` and to the target in `FIXED_TARGET`.
`acceptScore(key, costs)` supplies a complete cost vector of the solution's score type and dimensions,
with a zero structural component and nonnegative business components.
Replacing the vector preserves the feature's separate penalty histories at every level.
`acceptFloat` and `acceptDouble` use the exact represented binary value.
Automatic and custom features have separate key spaces.
Use `COMBINED` to include both families or `CUSTOM` to use only the provider.

Use costs in the corresponding score level's units. For example, guiding scaled distance with unscaled kilometers
changes the effect of `penaltyFactor` by the scale factor.

`extractFeatures` is the independent reference for correctness assertions.
It must read the supplied solution, not a session's caches or its previously emitted feature map.
The session is required for actual search; GreyCOS does not silently substitute full extraction for missing incremental logic.

Session callbacks cover basic genuine and shadow variables, list changes, and list-element assignment and unassignment.
Record affected objects in these callbacks and coalesce repeated notifications.
Resolve derived feature costs in `flushChanges` after shadow updates have settled.
`resetWorkingSolution` invalidates the old solution's caches; initialize lazily at the next safe flush.
A session must handle temporary candidate changes, undo, and committed moves identically.
Undo can restore a predicted business score without calling its calculator, so feature flushing must not depend on
`calculateScore()` being invoked.

Each working score director, including each move worker, receives its own session.
Provider instances can be shared by workers and must be stateless or thread-safe.
Sessions must not share mutable state or retain the consumer/updater outside the callback that received it.
Core owns penalty counters and the active penalty total; sessions report only feature presence and cost changes.
Do not modify planning variables, constraint weights, or the solution's score from a feature callback.

=== Routing features

The example provider uses directed arcs with typed customer/depot IDs, including depot departure and return.
Customer IDs distinguish visits even when their locations coincide.
Its cost is the same scaled distance used by the routing constraints.
The reference extractor walks vehicle lists independently of shadow caches.
The session updates cached arcs after predecessor, successor, or vehicle changes and ignores index-only changes.

Relocation and swap update adjacent arcs without a whole-route feature scan.
Reversing a segment changes every directed internal arc and requires corresponding updates.
If costs depend on the assigned vehicle, transferring a segment may change every transferred arc's cost.
Define explicitly whether a vehicle or cost class belongs in the key: sharing an arc key across vehicles shares its penalty history.
The example's distance costs do not depend on vehicle identity.

Constraint matches are not automatically used as GLS features.
A match involving one customer may depend on its predecessor, while a customer ID alone does not identify that arc.
Grouped matches and arbitrary justifications also need not describe elementary decisions.
Both automatic features and explicit providers work with Easy, Incremental, and Constraint Streams score calculation.

[#guidedLocalSearchLifecycle]
== Threading, islands, and diagnosis

Move workers evaluate guidance with private feature sessions against frozen penalty, focus, cost, and scale generations.
The coordinator consumes results in candidate order and synchronizes workers before changing guidance.
Published solutions and scores remain original-score results.
For reproducibility, keep the input, seed, selector configuration, worker count, and non-time termination fixed.
Wall-clock termination and concurrent island migration can change the trajectory.

Each island owns its controller, penalty history, and learned costs and scales.
Adopting a migrant resets those states and rebuilds the guided baseline from the adopted business solution.
Phase restart and problem changes also reset controller, learning, and feature state.
A configured new-best reset clears penalties after recording the original best; learned costs and scales remain available.

DEBUG logging reports rounds, penalty updates, and the controller state; phase summaries include GLS counters.
Distinguish consumed candidate evaluations from speculative work discarded by move workers.
The internal controller diagnostic snapshot also reports attempted, doable, and admissible candidates;
penalty updates and incremented features by score level; and committed moves by focus, state, and acceptance reason.
Attempt counts include prefetched work canceled after selection. Doable and admissible counts cover consumed results.
Committed counters use the focus and state at selection, before the following transition.
Directed selection reports eligible source draws, returned origins, and ordinary returned origins.
These phase totals survive migrant adoption; published scale observation counts describe the current rolling windows.
Retry exhaustion and failed excursion repair are normal phase-ending reasons, not completed search steps.
Use `FULL_ASSERT`, `TRACKED_FULL_ASSERT`, or `NON_INTRUSIVE_FULL_ASSERT` to compare incremental feature maps
and penalties against independent extraction. These full checks add whole-solution work to candidate evaluation.
When guidance is ineffective, check that keys distinguish the intended decisions, costs match the target level's units,
and movable positive-cost features are present.
If an infeasible start ends with `EXCURSION_REPAIR_EXHAUSTED`, inspect the repair-move count before extending the wall-clock limit.
The repair limit can end the phase while improving moves are still available.
The cloud example sets `excursionRepairStepLimit=1024` because its overloaded 120-process input required
more than the default 64 repair moves in the bounded comparison. The global default remains 64.

[#guidedLocalSearchBenchmarking]
== Measuring effectiveness

For throughput measurements, disable assertions and compare the same initialized inputs, seeds, neighborhoods,
worker counts, and solve budgets. Measure original score and feasibility together with candidate throughput,
penalty rounds, and memory. A faster feature evaluator alone does not establish better solution quality.

The opt-in routing and cloud benchmarks under `examples/src/test/java/examples` export input and artifact hashes,
initialized assignments, effective configurations, original-score trajectories, diagnostics, and independently replayed results.
Use saved construction-heuristic starts for paired comparisons and verify their assignments and scores before measuring search.
Preserve the effective construction configuration, including explicit nearby selectors and any enabled automatic nearby selection.
Use `NONE` for sequential search; a move-thread count of `1` creates one move worker.

A bounded upgrade comparison can use this 120-minute maximum budget:

[cols="3,1",options="header"]
|===
|Work |Budget
|Routing `n1000`: previous supplied GLS, upgraded automatic GLS, and the application Late Acceptance configuration;
three seeds, 600 seconds per run |90 minutes
|Routing `n100` and cloud `c40-p120`: old and new automatic GLS, construction-heuristic and overloaded starts,
`NONE` and six workers, three seeds, 15 seconds per run |12 minutes
|Screening on a separate seed, including old and new engines with identical settings |6 minutes
|Warmup, start preparation, setup, and termination overhead |12 minutes
|===

Retain executable artifacts of the previous implementation for the baseline.
For the supplied routing comparison, record its explicit factor `0.01`, sample size `1000000`, and six move workers.
The upgraded automatic arm uses factor `0.1`, sample size `1000`, and six move workers.
The application reference uses four Late Acceptance islands, three move workers per island, and history size 200.
Report that larger worker topology; it is an application reference with a different CPU allocation.
Freeze selected settings before measuring the three comparison seeds.

Run measured solves sequentially with hard time limits and record early phase endings.
The optional benchmark property `unimprovedMillis=120000` stops a run after two minutes
without an original-best improvement, while retaining its configured total time cap.
It applies to the entire measured phase, including the application island phase.
The default is zero, which disables this cutoff. Checkpoints after early termination are recorded as `NA`.
Extract 60-, 120-, 300-, and 600-second checkpoints from the long runs instead of repeating them.
Report every seed's feasibility, best original score, time to feasibility, useful consumed evaluations,
discarded evaluations, penalty updates, and excursion outcomes.
Replay every exported result independently.
Compare routing distances and cloud objectives separately.

For this upgrade comparison, judge the final feasible routing distance at 600 seconds and progress beyond
the previous implementation's plateau. Slower initial convergence is acceptable; the 60-second checkpoint
is diagnostic rather than an acceptance gate. Record time to the reference target and periods without
improvement so an early plateau is distinguishable from continued progress.
When an idle cutoff ends a run sooner, compare its final score at the actual stopping time and state that
the later checkpoints were not measured. A retrospective truncation of an earlier trajectory must be labeled as such.
These are measured acceptance criteria, not CI timing assertions or established results.
Record whether and when the reported routing reference of 56.1 is reached.
